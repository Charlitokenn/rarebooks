# Review, main, 2026-10-26

**Reviewed by**: claude-opus-5-5 (author on sonnet)
**Scope**: 62 files, whole-code audit of committed `worker/`, `custom/web/`, `src/web/`, `rendererWeb.ts`, `vite.config.web.ts`, `fyo/demux/*.ts` (web branches), plus 5 untracked worker tests. No branch diff, since main equals base.
**Verdict**: Changes requested

## Summary
This audit covers the spec 0001 web foundation: a Hono Worker with Clerk session middleware, a svix-verified `organization.created` webhook that provisions a Neon project per tenant, AES-256-GCM storage of the connection string, tenant resolution with a short TTL cache, dashboard gating by tenant status, and the fetch-based demux layer. The security core is solid. The session org is the only source of tenant identity, the webhook is verified before any side effect, and plaintext connection strings are never cached, logged or returned. The worker tests cover all of this well. The main problems are in the provisioning lifecycle. A provisioning claim that gets interrupted is never recovered. Neon projects can be orphaned on failure. The client never re-checks a `PROVISIONING` tenant, so the new-org happy path can sit on a spinner until the user reloads.

## Major

### 🟠 An interrupted provisioning claim leaves the org stuck in PROVISIONING for good, `custom/web/auth/handleOrganizationCreated.ts:73`
**Problem**: The webhook request does all of the work synchronously: `claimTenantProject`, then Neon `createAndConnect()` (which polls the operation until it completes), then encrypt, then write `PROJECT_CREATED`, then the full `DatabaseCore.migrate()` and seeding. If that request dies after the claim and before `failTenantProjectClaim`, the row stays `PROVISIONING` with a non-null `provisioning_claim_id`. Causes include a Svix delivery timeout followed by client-disconnect cancellation, isolate eviction, a deploy, or a CPU limit. Nothing ever releases that row:
- `claimTenantProject` (`worker/db/control.ts:126`) only reclaims rows whose status is `FAILED`.
- `claimTenantProjectMigration` (`control.ts:84-85`) only matches `PROJECT_CREATED` with a null claim.
- When a Svix retry arrives, both claims return nothing, so `handleOrganizationCreated` returns quietly (`:80-82`). The route then answers 200 (`worker/routes/webhooks/organization-created.ts:83`) and Svix stops retrying.

The same applies when the death happens during `applySchema`: the row stays `PROJECT_CREATED` with the claim held, and only the operator runner can recover it.
**Why it matters**: This contradicts the spec's critical failure scenario ("`tenant_projects.status` is set to `FAILED`, not left `PROVISIONING` indefinitely"). The org can never reach the dashboard, and nothing alerts anyone. Provisioning plus migrating roughly 100 tables over WebSocket round trips can easily take longer than Svix's delivery timeout, so this is a likely path, not an edge case.
**Suggested fix**:
- Give claims a lease: add a claimed-at timestamp, and let `claimTenantProject` / `claimTenantProjectMigration` take over a claim older than N minutes.
- Return a non-2xx response when a duplicate delivery finds an in-flight claim, so Svix keeps retrying until the row settles.
- Ideally, acknowledge the webhook quickly and move provisioning into `c.executionCtx.waitUntil` or a Queue, so the work does not depend on the HTTP delivery staying alive.

### 🟠 Failure paths orphan Neon projects and lose their IDs, `custom/web/auth/handleOrganizationCreated.ts:114`
**Problem**: Two paths create a Neon project and then lose track of it:
- `createAndConnect()` succeeds, but encryption or `insertTenantProject` throws (a control-plane blip, or a lost claim). The catch marks the row `FAILED` without ever recording `provisioned.neonProjectId`, and nothing deletes the project.
- `applySchema` fails, so the row goes to `FAILED` (`:123`). On any later replay, `claimTenantProject`'s `ON CONFLICT ... WHERE status = 'FAILED'` branch (`worker/db/control.ts:120-126`) blanks `neon_project_id` and `connection_string` and provisions a second project. The first project, which may hold partial schema, is now unreferenced.
**Why it matters**: Every orphan is a billed Neon project that nothing in the system refers to. The spec already calls out per-signup provisioning cost, and these leaks add to it silently. Because the ID is gone, nobody can clean up or investigate later.
**Suggested fix**:
- Persist `neon_project_id` before any step that can fail after `createAndConnect`. Alternatively, best-effort delete the project in the catch.
- In the FAILED reclaim branch, reuse an existing non-empty `neon_project_id` (go back to migration), or delete it before provisioning a new one, rather than overwriting it.

### 🟠 The client never re-checks a PROVISIONING tenant, so new orgs can sit on an endless spinner, `src/web/shellBootState.ts:24`
**Problem**: `PROVISIONING` maps to `{ kind: 'booting' }`. `WebShell.vue:19-48` renders that as a spinner with no Retry button. The docblock says "let the next navigation or Retry re-check", but:
- `ensureShellReady()` is called only from `WebShell.mounted`, Retry, and Clerk listener transitions.
- Child-route navigation does not remount the shell.
- The booting view has no Retry button.

`CreateOrganization.vue` sends the user to `/dashboard`, which now redirects to `/`, and its comment (line 5) still says "Dashboard.vue itself polls". `src/pages/web/Dashboard.vue` is no longer routed, so the polling it did was lost when the shell replaced it. Immediately after org creation, `/api/dashboard` almost always returns 202 `PROVISIONING`: there is either no row yet (webhook lag) or the webhook is still running.
**Why it matters**: The main path in AC-5 (sign up, create org, reach the shell) stalls on "Your account is still being set up." until a manual reload. The same happens for a tenant stuck as described in the first finding, with no exit.
**Suggested fix**: Poll `ensureShellReady()` with backoff while the state is `PROVISIONING` or `PROJECT_CREATED`, and stop on `ready` or `unavailable`. Also either give the booting state a Retry button or map `PROVISIONING` to the `unavailable` + `stillProvisioning` screen that `PROJECT_CREATED` already uses. Update the `shellBootState` test and the stale comment in `CreateOrganization.vue`.

## Minor

### 🟡 Webhook path differs from the spec, `worker/index.ts:31`
**Problem**: The webhook is mounted at `/webhooks/organization-created`, but the spec's API table says `/webhooks/clerk/organization-created`. `app-routing.spec.ts` deliberately pins the new path ("old spec path" returns 404).
**Why it matters**: The spec is the record that operators and later features consult. As it stands, it would lead someone to register the wrong URL in Clerk.
**Suggested fix**: Update the spec 0001 API surface table (through /architect or /sync) to match the URL that is actually deployed.

### 🟡 Raw database error messages are returned to the client, `worker/routes/db.ts:119`
**Problem**: Both `/call` and `/bespoke` (`:160`) return `err.message` with a 422 for any non-validation failure. Knex and pg errors can contain SQL text, table and constraint names, and driver connection details.
**Why it matters**: This leaks internal detail to the browser. It falls under spec 0002, but it sits right next to the AC-4 "never exposed" boundary.
**Suggested fix**: Map known validation and constraint errors to safe messages. Log everything else on the server and return a generic error body.

### 🟡 Ciphertext is not bound to its org, `worker/lib/encryption.ts:37`
**Problem**: AES-GCM is used without `additionalData`. Someone who can write the control plane could copy one org's `connection_string` ciphertext into another org's row, and it would still decrypt.
**Why it matters**: This is defence in depth for the isolation guarantee, not a vulnerability on its own.
**Suggested fix**: Pass `additionalData: TextEncoder(orgId)` on encrypt and decrypt. This needs a one-off re-encrypt of existing rows.

### 🟡 clerkMiddleware has no authorizedParties, `worker/index.ts:20`
**Problem**: `clerkMiddleware()` is called with no options.
**Why it matters**: Clerk recommends setting `authorizedParties` so that session tokens minted for other origins, such as a sibling subdomain, are rejected. `SameSite=Lax` on `__session` already mitigates classic CSRF.
**Suggested fix**: Pass `authorizedParties: ['https://app.rarebooks.cc', ...]`, read from env.

### 🟡 staging and production envs may inherit the production custom domain, `worker/wrangler.toml:23`
**Problem**: `[[routes]]` (`app.rarebooks.cc`, `custom_domain = true`) and `[assets]` are top-level keys. The `[env.staging]` and `[env.production]` sections only override `name`. In wrangler, `routes` is an inheritable key.
**Why it matters**: If `routes` is inherited, `deploy:staging` would try to bind the production domain to the staging worker. I am fairly but not fully confident `routes` is inheritable, so verify this against wrangler's environment docs.
**Suggested fix**: Give each env its own `routes` (or `routes = []` for staging), and say explicitly which env owns `app.rarebooks.cc`.

### 🟡 Two copies of the readiness check, and the demux one has a stale comment, `fyo/demux/db.ts:150`
**Problem**: The web branch of `connectToDatabase` still says `getSchemaMap` is NotImplemented "until feature 0002" (it now exists). It also returns the tenant *status* as the dbPath. Meanwhile `src/web/boot.ts:92` makes its own raw `fetch('/api/dashboard')` outside the demux.
**Why it matters**: There are now two copies of the same platform call, which works against the AGENTS rule that platform calls go through demux. The misleading comment invites someone to misuse it.
**Suggested fix**: Pick one path, ideally a demux method that returns the tenant status, and have `boot.ts` call it. Fix or remove the stale comment.

### 🟡 Orphaned `src/pages/web/Dashboard.vue` and comments that point at it
**Problem**: `Dashboard.vue` is no longer in `src/web/router.ts`. `CreateOrganization.vue:5` and `src/web/boot.ts:27` still describe it as live.
**Why it matters**: Dead code plus stale docs hid the polling regression described in the third Major finding.
**Suggested fix**: Delete the page, or reuse its polling logic for the fix in that finding, and update both comments.

### 🟡 The control-plane claim SQL is never run in tests, `worker/db/control.ts:106`
**Problem**: Every test mocks `control.ts`. The provisioning race-safety lives entirely in its `WHERE` clauses: `ON CONFLICT ... WHERE status = 'FAILED'`, the claim-id guards, and `RETURNING` row counts. None of that ever executes. I traced it by hand and it looks correct, but nothing protects it from regressions.
**Why it matters**: A single changed predicate could allow double provisioning, or block retries, and the tests would still pass.
**Suggested fix**: Add a small integration test against pg-mem or a Neon branch covering claim, duplicate claim, fail then reclaim, and lost-claim completion.

### 🟡 Subscription 402s still reach the generic error handler, `rendererWeb.ts:124`
**Problem**: `initSubscriptionRedirect` calls `event.preventDefault()` (`src/web/subscription.ts:66`), but that does not stop the `window.onunhandledrejection` handler installed earlier. `handleError` still runs for every `SubscriptionInactiveError`.
**Why it matters**: A routine billing redirect may also produce an error toast or report.
**Suggested fix**: Have `onunhandledrejection` skip `SubscriptionInactiveError`, or route both through a single handler.

## Nits
- ⚪ `worker/lib/encryption.ts:19`: `importKey` re-imports the key on every call. Caching the `CryptoKey` per raw key would avoid that.
- ⚪ `worker/index.ts:20`: `clerkMiddleware` also runs on `/webhooks/*` and `/api/health`, which need no session. Scoping it to `/api/*` would save the work.
- ⚪ `src/web/shell.ts:110`: `org:owner` is not a default Clerk role. Either remove it or document the custom role.
- ⚪ `worker/package.json:22`: the `"rarebooks": "file:.."` dependency is unexplained. Add a note on why the worker depends on the root package.

## Strengths
- Tenant identity comes only from the verified Clerk session (`requireOrgSession`). A test explicitly attacks with `?orgId=` and an `x-org-id` header and confirms both are ignored.
- The webhook verifies before any side effect, passes the signing secret explicitly (Workers has no `process.env`), and has tests showing a bad signature never reaches `insertOrganization` or `claimTenantProject`.
- The encryption is correct: random 96-bit IV, strict 32-byte key check, and tests for tamper detection and wrong keys using real Web Crypto. The resolver caches only ciphertext, and a test checks that one org's cached connection is never served to another.
- The `knexPgConfig.ts` driver override is a well-diagnosed, well-documented fix for the Workers bundler stubbing out `pg`.
- The boot-epoch guard in `fyo/demux/db.ts` keeps responses from a previous org from landing after an org switch.
